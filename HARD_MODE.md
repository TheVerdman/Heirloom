# Hard Mode Notes

This file tracks what blocks the prototype from becoming real PyTorch parity. It should grow as the implementation gets more honest.

## Tensor Semantics

- `f32`, `bf16`, `f64`, `i64`, and `bool` storage exist, with small promotion rules and typed `.npy` IO for the non-bf16 CPU dtypes. A narrow differentiable BF16 activation-rounding path exists, but real parity still needs many more dtypes, exact PyTorch promotion behavior, scalar tensor semantics, complex numbers, quantized tensors, float16, production mixed precision policy, and exhaustive dtype/kernel coverage.
- CPU remains the only broad/general model training backend. `Device::Cuda(id)` and CUDA storage copies now exist, backed by primary-context `heirloom-kernels::cuda::CudaBuffer` handles. Contiguous full-storage f32 arithmetic, f32<->bf16 casts, ReLU, GELU, rank-2 dense/strided matmul, `[rows, cols] + [cols]` bias-add broadcasting, embedding gather/scatter-add, last-dimension layer norm, rank-2 cross-entropy, strict fused causal attention, and all-element sum/mean can execute forward and backward as first Tensor-level CUDA kernels, and narrow f32 CUDA SGD/AdamW update kernels exist. Concrete modules and `train-lm` can run a tiny CUDA CLI LM fixture with loss decrease and checkpoint resume on an A100, plus a full TinyStories-valid single-A100 CUDA public-data gate with train/eval/generate reports. A first NCCL DDP seam now exists for one-rank-per-GPU gradient averaging, and sm80 BF16 Tensor Core kernels exist for `Linear` forward plus input/weight backward matmuls with explicit device-side pad/crop edge handling, a default four-warp shared-memory-staged CTA launch path, and an opt-in eight-warp XOR-swizzled CTA launch path, as well as boundary-predicated causal-attention QK/AV forward plus score-grad/dQ/dK/dV backward matmuls for ragged `time`/`head_dim` edges. Guarded GEMM-only throughput tiers now include A100 microbench-validated `ldmatrix` shared-memory MMA and double-buffered `cp.async` staging kernels, but they are not default train-path production kernels. A 4x A100 Vertex worker exposed NV12 links and peer access across all pairs, and the staged launcher has now completed clean four-rank NCCL init plus f32 all-reduce probes. A bounded 4x A100 DDP tiny fixture has completed with loss decrease, checkpoint resume, positive NCCL gradient all-reduce stats, positive Tensor Core Linear counters, and zero final/per-step parameter-checksum drift. A bounded 4x TinyStories DDP reference tier has completed on a 1 MiB validation-split slice, and the full 500-step 4x TinyStories-valid DDP gate has completed with train/eval/generate reports, checkpoint-resume evidence, NCCL gradient all-reduce stats, Tensor Core Linear and attention coverage, and zero parameter-checksum drift. A first stream/event-aware CUDA runtime layer, per-thread caching allocator, module cache, runtime counters, strict AMP BF16 policy/staging report, finite-check report, and `amp_bf16_validation` gate now exist. Production-scale AMP parity, train-path production routing for the new instruction-path GEMM tiers, tuned/general/batched Tensor Core GEMM, production flash attention forward/backward, peer copies, multi-node distributed training, and production GPU model training still do not.
- Layout support is limited to dense strided tensors. There is no sparse, channels-last, nested, ragged, MKLDNN, meta, or lazy layout.
- View support is real but still narrow. `transpose`, `permute`, `narrow`, `expand`, contiguous `view`, and reshape-copy fallback work. CUDA autograd now has dense passthrough for `view` and a rank-2 transpose backward kernel, but rich slicing, indexing, differentiable `as_strided`, general overlap analysis, general CUDA view kernels, and negative strides are missing.
- Gradients are now f64 gradient tensors with storage, shape, strides, offset, dtype, and device metadata. This is only phase one: gradient tensors own independent storage, exact overlap analysis is still missing, and alias-aware accumulation across tensor handles is not solved.
- `ALIASING.md` tracks the production plan for view replay, overlap analysis, in-place rules, and alias-aware accumulation.
- There is a shared storage version counter and `add_`, but not PyTorch's full in-place/view validation model.
- No tensor indexing API.
- Broadcasting exists for basic binary arithmetic, but not as a general TensorIterator-equivalent across arbitrary kernels.

## Autograd

- Backward is single-threaded and recursive during graph discovery.
- `detach`, `no_grad`, saved tensor version checks, explicit non-scalar `backward_with_grad`, default graph release, and explicit retained backward APIs exist.
- No higher-order gradients, arbitrary custom autograd functions, saved tensor hooks, anomaly detection, activation checkpointing, or rich saved tensor lifecycle policy.
- No implicit gradient creation for non-scalar `backward`; callers must explicitly pass a seed gradient.
- Floating gradients are stored internally as f64 gradient tensors. Non-overlapping view gradients can preserve strides and storage offsets, while internally overlapping layouts fall back to dense gradient storage. Non-leaf gradients are transient by default and can be retained explicitly with `retain_grad`. Tensor gradient hooks can inspect or replace incoming gradients before accumulation. There is still no dtype-preserving gradient policy, saved-tensor hook system, higher-order hook semantics, or alias graph.
- No accumulation into shared gradient storage for aliased tensor handles; gradients remain attached to tensor identities.

## Ops And Numerics

- `matmul` supports rank-2 and batched matmul with broadcasted batch dimensions. PyTorch still supports a much broader vector/matrix/batched linear algebra surface.
- Reductions include all-element and single-dimension `sum_dim`/`mean_dim` with `keepdim`, plus signed-dim wrappers. Multi-dim reductions, named dimensions, dtype override, and numerically stable variants are missing.
- `mean` and `mse_loss` reject empty tensors instead of matching PyTorch's NaN/edge semantics.
- `relu` uses a fixed zero derivative at exactly zero.
- `sub`, `mul`, `div`, `softmax_dim`, `embedding`, `gelu`, `layer_norm_last_dim`, `masked_fill`, fused causal self-attention, and rank-2 fused cross-entropy exist. Many other primitive ops are still missing, and `mse_loss`/cross-entropy only support mean-style reductions.
- Most forward and backward paths fully materialize logical tensor data into temporary contiguous `Vec<f64>` buffers before computing. This is intentionally correctness-first, but it is categorically not a production CPU kernel strategy.
- No BLAS, SIMD, cache blocking, parallelism, or numerical accuracy work.

## Dispatcher And Backends

- A builtin operator catalog and `KernelRegistry` now describe operator identity, kind, dtype rules, alias policy, autograd policy, and CPU kernel resolution for the supported surface, including transformer-critical ops such as embedding, GELU, layer norm, masked fill, argmax, and fused causal attention. Tensor methods consult fresh-output and autograd policies when recording supported out-of-place ops.
- `DISPATCH.md` tracks the production plan for schema objects, dynamic registration, dispatch keys, boxed calls, and autograd kernel registration.
- No real dispatch keys, dynamic registration, generated schemas, boxed calling convention, backend fallback, custom backend hook, extension ABI, per-dtype/per-device kernel table, or schema entry for in-place variants such as `add_`. Transformer kernels and backward node construction are still Tensor-owned rather than registered dispatcher/autograd kernels.
- CUDA storage and first f32 Tensor forward/backward kernels exist for strict contiguous arithmetic, f32<->bf16 casts, ReLU, GELU, rank-2 dense/strided matmul, Linear-shaped bias add and view/transpose propagation, embedding gather/scatter-add, last-dimension layer norm, rank-2 cross-entropy, strict fused causal attention, and all-element sum/mean, plus narrow f32 SGD and AdamW parameter updates. NCCL is dynamically loaded in `heirloom-kernels`, and a safe communicator wrapper can all-reduce f32 CUDA buffers for DDP gradient averaging. A BF16 Tensor Core `mma.sync` probe and `A[M,K] * W[N,K]^T -> C[M,N]` GEMM wrapper exist for sm80+ `Linear` projections, including compatible forward and input/weight backward matmuls under AMP; ragged dimensions are padded on device to MMA tile boundaries and cropped back to logical f32 outputs with padded/remainder counters. The default Linear Tensor Core kernel is now a four-warp shared-memory staged CTA launch over 32x16 output regions: each CTA cooperatively stages A/RHS BF16 tiles into shared memory for every K slice, then feeds four `m16n8k16` MMA warp tiles. An opt-in eight-warp, 32x32 output-region, XOR-swizzled shared-memory CTA kernel exists behind `HEIRLOOM_CUDA_TENSOR_CORE_WIDE_SWIZZLED_GEMM=1` and has live A100 fixture coverage. Guarded `HEIRLOOM_CUDA_TENSOR_CORE_LDMATRIX_GEMM=1` and `HEIRLOOM_CUDA_TENSOR_CORE_CP_ASYNC_GEMM=1` tiers now launch A100 microbench-validated instruction-path GEMM kernels, but they are still throughput gates rather than default train-path production kernels. Runtime reports distinguish CTA GEMM calls, CTA tiles, launched CTA warps, active MMA warp tiles, staged CTA calls, shared-stage tiles/bytes, wide-swizzled CTA calls, swizzled-stage tiles/bytes, ldmatrix/cp.async calls and instruction counters, global-fed CTA debug calls, and legacy one-warp GEMM calls. Train reports promote pad/crop into a named `tensor_core_pad_crop` section with logical/padded shapes and fallback status, and the GCP fixture uploads compact pad/crop summaries for reviewer inspection. This is better engine structure and reportability, not tuned GEMM performance: bank-conflict-tuned shared-memory layouts, deeper tiling, occupancy tuning, and a general batched GEMM interface remain open. A Tensor Core causal-attention path now exists for QK/AV forward and score-grad/dQ/dK/dV backward matmuls, including predicated ragged `time` and `head_dim` edges with attention padded/remainder/fallback counters; f32 CUDA kernels still handle the softmax backward and transpose glue. The Tensor Core tiled flash forward candidate has a separate A100 attention-only forward gate, but remains an isolated no-grad throughput path until flash backward exists. A first per-thread CUDA caching allocator, stream/event wrapper, deferred-free queue, module cache, and profiler-style runtime counters now exist, but they are not a production allocator or scheduler. Everything else intentionally errors or falls back until kernels are registered. There is no general GPU autograd engine, no GPU batched Tensor Core matmul, no peer-copy layer, no multi-stream scheduler, no pinned host-memory pipeline, no cuBLAS/cuDNN, no CUDA graphs, no production FlashAttention-style forward/backward, and no production AMP parity.
- A Rust-side `CustomUnaryOp` API and separate `CustomUnaryRegistry` exist for floating, shape-preserving unary ops with custom backward. There is no custom binary/reduction/view/in-place/multi-output op support, builtin catalog insertion, C/Python ABI, plugin loading, or backend-specific custom kernel.
- Device synchronization, stream semantics, and allocator abstraction now have a first narrow CUDA implementation. They are still missing production pieces: stream priorities, cross-stream dependency graphs, allocator defragmentation, memory pools across threads/processes, pinned memory, async H2D/D2H copies, graph capture, and robust profiling integration.

## Modules And Training

- `Module` is minimal. Concrete module types now expose narrow `.to_device(Device)` helpers, but there is no parameter registration macro, buffers, train/eval mode, recursive trait-object device movement, scheduler support, or rich serialization contract.
- A separate `MemoryTransformerLm` exists with exact memory lookup, CPU/CUDA product-key-style candidate lookup over trainable left/right half-key tables, shared memory tables, Memory+ style gating, checkpoint family metadata, foreground SMFT access-count reports, TF-IDF-like SMFT row-mask derivation from foreground/background counts, explicit `train-memory-lm --smft-row-mask` input, file-backed foreground/background SMFT count and mask artifacts, optional online SMFT mask refresh for sparse-row memory updates, conservative product-key full-slot-to-half-key mask projection, `train-memory-lm --distributed nccl` support for `Full`/`MemoryOnly` memory updates plus `SparseRows` row-union synchronization, compact sparse-gradient all-reduce, and offline SMFT row-mask intersection, rank reports proving memory-table gradient presence/checksum sync/row-union all-reduces/compact gradient all-reduces/SMFT mask metadata, and CUDA kernels for exact memory top-k, product-key candidate routing, product-key selected-score forward/backward, weighted-value aggregation/backward, selected-row gradient gather, selected-row access counting, selected-row-to-mask row union, bool mask intersection, Bool-mask-to-row-index compaction, and compact selected-row AdamW updates. This is still not paper-grade memory-layer parity: product-key lookup is a scalar beam candidate path rather than a production large-memory index, product-key SMFT half-key masks are conservative and can freeze more half-key rows than the selected full-slot mask, sparse-row optimizer modes still accumulate dense CUDA gradient buffers inside each rank before gathering compact selected gradient rows, compressed sparse-gradient transport is only wired for the narrow `SparseRows` memory-table DDP path and still needs live A100 validation, online refresh uses accumulated foreground counts inside one run rather than a production background-corpus/windowed refresh pipeline, distributed SMFT background-count mask generation and refresh synchronization are not implemented, and memory-transformer DDP/A100 validation remains pending.
- `Sgd` exists, including a narrow CUDA f32 update path for contiguous full-storage parameters, but it has no momentum, weight decay, parameter groups, or state serialization.
- `AdamW` exists with moment state, weight decay, clipping, JSON state serialization, a narrow CUDA f32 update path with CUDA-resident moment buffers, and NCCL gradient averaging before local CUDA AdamW in the DDP path. It still has no parameter groups, schedulers, production mixed precision optimizer policy, production fused optimizer kernels, rich optimizer hooks, optimizer-state sharding, or true multi-device optimizer state.
- state_dict save/load exists for named parameters, and LM checkpoints bundle model, optimizer, tokenizer, config, step, dataset RNG state, dataset batch count, and an optional prepared-dataset manifest path. CUDA model checkpoints save CPU snapshots and can reload onto a requested device. This is still a narrow directory format, not a production checkpoint archive.
- Heirloom RNG exists, but it is not PyTorch RNG parity and has no per-device generators, distribution library, or reproducibility contract across future algorithm changes.
- Generation now supports seeded temperature/top-k/top-p sampling plus repetition, frequency, and presence penalties, with JSON reports and an explicit f32/BF16 activation precision flag. This is still not a production decoding stack: no beam search, constrained decoding, tokenizer stop strings, batched serving, KV cache, streaming output, logit processors as extensions, or robust text-quality evaluation.
- `eval-lm` computes deterministic heldout cross-entropy and perplexity over token windows and can emit JSON reports with an explicit f32/BF16/AMP policy flag plus AMP validation metadata. It is not a general evaluator: no distributed/sharded evaluation, no document-boundary masking, no stride/overlap policy options, no multiple metrics, no calibration analysis, and no benchmark harness.

## IO And Serialization

- Pure Rust `.npy` read/write exists for CPU f32/f64/i64/bool C-order tensors. BF16 tensors are rejected by `.npy` until a real serialization policy is chosen.
- No `.npz`, safetensors, pickle, PyTorch `.pt`, memory mapping, streaming IO, compression, atomic writes, content-addressed artifacts, or metadata-rich checkpoint format.
- `.npy` parsing is intentionally narrow and should not be treated as a complete NumPy format implementation.
- Tokenizer JSON is versioned and load-validated, but the tokenizer is still a small byte-level BPE-like implementation, not GPT-2-compatible BPE, SentencePiece, Unigram, or a production tokenizer with normalization/pretokenization policy.
- Prepared language-model data now writes train/valid token files with source/tokenizer hashes and a manifest, checkpoints can resume dataset RNG/batch state, and DDP ranks can derive deterministic sharded batches from `(seed, global_step, rank, sample_index)`. This still materializes token arrays as JSON, has no streaming/sharded format, no mmap, no packed-document boundary handling, no production distributed sampler, no multiprocessing workers, no pinned-memory prefetch, no corruption recovery beyond hash checks, and no general dataset abstraction.

## Python Interop

- A thin PyO3/maturin binding crate now exists as `heirloom-python`, producing a `heirloom_py` module for direct Python parity tests against live PyTorch. It exposes Tensor construction, metadata, materialization, core ops, selected transformer ops, losses, backward, and gradients.
- This is not a production Python API. It has no module/optimizer/checkpoint/dataloader bindings, no Python custom autograd, no rich NumPy zero-copy buffer protocol, no `__array__`/DLPack/Torch interop, no Python packaging/release story, no typing stubs, no stable ABI policy, no Python-side graph/debug tooling, and no ergonomic PyTorch-like namespace.

## Testing And Parity

- Parity tests include static JSON fixtures consumed by Rust, a Python generator that can refresh them from live PyTorch, and a live `heirloom_py` pytest suite that compares the binding directly against `torch`.
- Live fixture generation uses the committed `uv.lock` and `.venv-parity` environment with CPU `torch 2.12.0`; the checked fixture was refreshed from actual PyTorch and includes transformer-runtime cases.
- Docker validation exists for CPU reproducibility. Hardware integration tests are explicitly ignored in the normal suite and fail loudly through `scripts/test_gpu.sh` when CUDA, NCCL, or required BF16 capability is absent. Historical Vertex A100 runs exercised the narrow CUDA/autograd/optimizer/Tensor Core and same-node NCCL paths described below, but those runs predate the current commit and pinned toolchain; see `docs/evidence/gpu-validation.md`. There is still no maintained CUDA container image, full production AMP parity path, or production-scale distributed validation.
- A TinyStories validation benchmark script exists, a small public-data CUDA reference run has completed on a 1 MiB validation-split slice, an `amp-bf16` public-data reference run has completed on the same tier with Tensor Core coverage, the full uncapped TinyStories-valid CUDA gate has completed on one A100 with CUDA train/eval/generate reports, a bounded 4x TinyStories DDP reference tier has completed with public-data train/eval/generation artifacts, and the full 4x TinyStories-valid DDP gate has completed with checkpoint-resume artifacts. The CUDA wrapper now has smoke/reference/full tiers with timing, config metadata, DDP metadata, rank-launcher artifacts, and optional resume reports. This is evidence of a narrow CUDA/DDP training path, not production GPU training parity.
- Property tests and finite-difference checks exist, but coverage is still tiny compared with PyTorch's real test matrix.
- Dtype tests cover a small matrix of constructors, BF16 casts, differentiable cast gradients, promotion, f64 autograd, reductions, non-float autograd rejection, typed `.npy` IO, BF16 activation training, and gated CUDA storage/math/autograd/optimizer round trips. CUDA matmul coverage now includes a transposed RHS view, Linear-shaped projection fixtures, a BF16 Tensor Core Linear forward/backward path with a gated ragged pad/crop fixture, and a BF16 Tensor Core attention forward/backward matmul fixture with ragged edge coverage, but general CUDA matmul backward is still FP32-kernel based and CUDA BF16-cast/GELU/embedding/layer-norm/cross-entropy/causal-attention/AdamW coverage is still a small fixed fixture set. There is still no fuzzing, sanitizer run, stress test, broad randomized dtype/device matrix, or large numerical tolerance study.

## Safety And Ownership

- `Rc<RefCell<_>>` is intentionally simple and single-threaded. Production Rust would need clearer ownership, thread-safety boundaries, and perhaps `Arc` plus interior mutability designed around execution semantics.
- Error handling is explicit but coarse. Real frameworks need precise diagnostics, source locations, and debuggability around graph construction.
